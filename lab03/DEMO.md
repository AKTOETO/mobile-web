# Демонстрация преподавателю — 3–5 минут

## Перед началом

1. Проверить Docker Engine (`docker --context default ps`) и запустить VirtualBox с Aurora.
2. Из корня репозитория выполнить:
   `./lab03/lab up -d --build --wait`.
3. Открыть **http://localhost:9084**. Должно быть 6 контейнеров `running / healthy`.
4. В Aurora открыть «Развёртывание Aurora», адрес — `http://10.0.2.2:9083`.
   Приложение можно запустить SSH-командой из README. Оно должно показывать каталог.
5. Закрыть автоматические тесты. Нажать «Сбросить счётчики» в панели.

## 1. Доказать балансировку

Нажать **«Балансировка»**. Сценарий подготавливает Blue и выполняет 40 запросов.

Показать:
- карточки blue1/blue2 — healthy;
- счётчики обеих реплик растут;
- в «Доказательствах» — `40/40 HTTP 200`;
- в журнале nginx чередуются адреса upstream и backend;
- в Aurora меняется имя REST-backend, push приходит от одной подключённой реплики.

Объяснение: «Каждый запрос проходит через nginx, backend определяется по
заголовку X-Backend. Это реальные ответы двух контейнеров, а не случайные числа
в интерфейсе. WebSocket привязан к одной реплике до переподключения».

## 2. Отключить один backend

Нажать **«Отказ реплики»**. Blue1 останется остановлен после сценария.

Показать:
- карточка blue1 — stopped/exited;
- blue2 продолжает отвечать, `40/40 HTTP 200`, ошибок — 0;
- приложение Aurora продолжает получать каталог через прежний URL;
- при попадании первого запроса на остановленный адрес журнал nginx содержит
  `502, 200` или `504, 200`: ошибка первой попытки и успешная повторная попытка.
  Docker DNS и выбор живой реплики могут привести к тому, что не каждый запуск
  даст такую строку; главным доказательством остаются остановленный контейнер
  и успешные запросы к другой реплике.

Остановка видна и стандартными средствами:
`./lab03/lab ps -a`.

Для демонстрации именно **разрыва push** посмотреть его текущий backend в Aurora
и остановить соответствующую карточку, оставив вторую реплику работающей.
Клиент автоматически переподключится. Не останавливать обе реплики одновременно
в основном сценарии отказоустойчивости.

Нажать **«Восстановить»**, дождаться healthy и подтверждения серии.

## 3. Обновить без остановки REST

Нажать **«Blue → Green»**.

Показать:
- поток запросов продолжается во время операции;
- доказательство `100/100`, версии `1.0.0 → 2.0.0`, ошибок непрерывного потока — 0;
- новые ответы идут от green1/green2;
- новый push — «Контроль дефицита: 1 поз.»;
- приложение Aurora также перешло на v2.0.0 без перезапуска.

Объяснение: «Сначала проверяется целевая пара, затем nginx проверяет конфиг и
делает graceful reload. Вторая версия уже запущена, но до переключения не получает
новые запросы. Backend-порты с хоста не опубликованы. Через пять секунд старые
WebSocket переподключаются; REST остаётся доступен».

## 4. Откат и доказательства

Нажать **«Откат на Blue»**, показать 100/100 и возврат версии.
Нажать **«Скачать JSON»**: в файле сохранены все пробы и метаданные сценариев.
При необходимости открыть `docker --context default stats` и `./lab03/lab ps -a`.

## Дополнительный сценарий: полный отказ

Остановить обе карточки активного цвета. Ошибки должны появиться — это честная
демонстрация отсутствия живых backend. Aurora показывает повтор и сохраняет каталог.
Запустить обе карточки или нажать «Восстановить»: запросы и push возобновятся.
После этого очистить счётчики перед новой демонстрацией, чтобы не смешивать
преднамеренный полный отказ с проверкой отказа одной реплики.
