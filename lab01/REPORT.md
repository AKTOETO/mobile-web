## 1. Задание

### 1.1 Состав отчёта

Первая лабораторная работа курса включает сразу два задания из файла заданий — №1 и №2.
Они выполняются как один проект: сервер с web-интерфейсом и мобильное приложение под
ОС Аврора, которое общается с этим сервером по web-socket-каналу. Вариант №7 в обоих
заданиях одинаковый, поэтому сервер один, а не два.

> **Лабораторная работа №1. Взаимодействие с web-клиентом.** Необходимо разработать
> серверное программное обеспечение на любом языке программирования, реализующее логику
> работы в соответствии с вариантом. Данное серверное обеспечение должно взаимодействовать
> с пользователем посредством браузера, иметь web-интерфейс. Для реализации web-интерфейса
> необходимо создать файлы html, css и js. Файлы js должны обеспечивать функции управления
> пользовательскими действиями, обрабатывать нажатия на кнопки web-формы. Кроме того,
> необходимо добавить асинхронный вызов js (async, promise и т. д.). В css файле обеспечить
> адаптивную верстку под различные разрешения экрана с использованием @media. Реализованное
> программное обеспечение запускается в локальной сети. Демонстрируется работа приложения
> в браузере десктопной ОС (ПК) и в браузере мобильного телефона под управлением ОС Аврора.
>
> **Лабораторная работа №2. Разработка мобильного клиента.** Необходимо разработать
> приложение на Qt (возможны варианты с flutter) для запуска на мобильном устройстве под
> управлением ОС Аврора. Данное приложение должно взаимодействовать с сервером посредством
> передачи данных через сокеты (web-сокеты). Запустить сервер на удаленном устройстве (ПК),
> обеспечить подключение мобильного устройства к серверу в локальной сети и взаимодействие
> приложения с сервером.
>
> **Вариант №7: Сервер статистики аналитики сайта.** Простое решение для сбора статистической
> информации о посетителях сайта: количество просмотров страниц, уникальные посетители,
> длительность сессий. Данные собираются асинхронно через JS и сохраняются на сервере
> с визуализацией результатов в виде графиков или диаграмм.

## 3. Выбор технологий и обоснование

1. **Node.js, только стандартные модули.** Задание требует «любой язык» и запуск в
   локальной сети. Нулевые зависимости означают, что сервер запускается одной командой
   `node server/server.js` без установки пакетов и без интернета — важно для демонстрации
   на защите.
2. **Хранение в JSON-файле.** Аналитике не нужны транзакции и связи; файл `data/stats.json`
   читаемый, его можно показать руками, загрузка и сохранение — асинхронные операции
   `fs/promises`.
3. **Графики на canvas собственным кодом.** Внешние библиотеки (Chart.js) требуют CDN или
   сборки; на телефоне с Аврора сеть может быть ограничена, а canvas есть в браузере Авроры.
4. **WebSocket без npm-пакетов.** Канал `/ws` реализован вручную по RFC 6455
   (`server/websocket.js`), чтобы работа №2 не добавила зависимостей в работу №1.
5. **Qt 5 + QML (Sailfish Silica) в приложении.** Это штатный стек Авроры: `CONFIG += auroraapp`
   и `QT += websockets` дают сборку через `sfdk build` и пакет RPM, который ставится на
   устройство пакетным менеджером.
6. **Логика клиента на C++, интерфейс на QML.** `StatClient` подписан через `Q_PROPERTY`,
   поэтому QML читает статистику как свойства и реагирует на сигналы; рисование графиков
   остаётся декларативным (`Canvas` в QML).
7. **Консервативный JavaScript в трекере.** Без optional chaining, nullish-оператора и
   стрелочных функций в критичном коде: браузер Авроры (Gecko/Sailfish) старше десктопных.
8. **Графики отчёта — Python/matplotlib.** Отдельный скрипт строит те же графики из того же
   файла `stats.json`, что даёт бумажную версию визуализации.

## 5. Работа №1. Сервер статистики и web-интерфейс

### 5.1 Модель данных

Три сущности: **посетитель**, **сессия**, **событие**. Посетитель идентифицируется UUID,
который клиент хранит в `localStorage` (поэтому посетитель «уникальный» и может возвращаться).
Сессия живёт в `sessionStorage` и на сервере; событие — это один запрос с клиента.

![Модель данных статистики](images/data-model.png)

| Сущность | Ключевые поля | Назначение |
|---|---|---|
| `visitor` | `id`, `firstSeen`, `lastSeen`, `visits`, `pageViews`, `ua`, `device`, `lang`, `screen`, `tz` | уникальные посетители, новые и вернувшиеся |
| `session` | `id`, `visitorId`, `start`, `lastEvent`, `end`, `closed`, `durationSec`, `pageViews`, `actions`, `entryPage`, `exitPage`, `referrer`, `device` | длительность сессий, глубина, отказ, вход и выход |
| `event` | `id`, `ts`, `type`, `visitorId`, `sessionId`, `page`, `label`, `referrer`, `device`, `ip` | просмотры страниц, нажатия кнопок, heartbeat |
| `feedback` | `ts`, `name`, `email`, `message`, `page` | демонстрация обработки web-формы |

Типы событий: `pageview` (просмотр страницы), `action` (нажатие кнопки формы),
`heartbeat` (страница открыта), `session_end` (страница закрыта).

### 5.2 Сервер, хранение и найденные ошибки

Сервер — `server/server.js` на встроенном `http`: маршрутизация `/api/*`, раздача статики
из `public/`, лимит тела запроса, CSV-экспорт. Хранение — `server/storage.js`: загрузка JSON
при старте, накопление событий в памяти, асинхронная запись на диск с debounce 400 мс,
ограничение размера (20000 событий, 5000 сессий).

**Ошибки учёта, найденные при проверке демо-данных и исправленные**

| Проблема | Симптом | Исправление |
|---|---|---|
| Суффикс `#N` добавлялся идентификатору сессии даже без конфликта | 35 реальных сессий считались как 85 | суффикс создаётся только при коллизии: `while (state.sessions[sessionId]) { … }` |
| События добавлялись в массив не по времени | `firstEvent > lastEvent`, пустые окна таймлайна, неверное усечение | `insertEvent()` — бинарная вставка по `ts`, массив событий всегда отсортирован |
| Внешние источники не появлялись в статистике | все демо-сессии помечались «внутренними» | referrer-ы в `seed.js` стали взвешенными (`pickWeighted`) |
| «Внутренний переход» определялся только по Host заголовку | сайт, открытый по `localhost` и по `127.0.0.1`, считался внешним | клиент передаёт `origin` своей страницы, сервер сравнивает хост referrer-а с хостом страницы |

### 5.3 HTTP API

| Метод и маршрут | Назначение | Ответ |
|---|---|---|
| `GET /api/health` | проверка живости, версия, время работы | JSON |
| `GET /api/stats?range=&page=&limit=` | полный отчёт для дашборда | JSON с KPI, таймлайном, топ-страницами, устройствами, сессиями |
| `GET /api/pages` | список страниц для селектора формы отчёта | JSON |
| `GET /api/sessions?limit=` | последние сессии | JSON |
| `GET /api/feedback` | отзывы, отправленные через форму | JSON |
| `POST /api/events` | приём события трекера (`pageview`, `action`, `heartbeat`) | `201` + краткая сводка |
| `POST /api/session-end` | закрытие сессии, фиксация длительности | JSON с сессией |
| `POST /api/feedback` | сохранение web-формы | `201` + запись |
| `GET /api/export.csv?type=…` | выгрузка CSV (`;` разделитель, UTF-8 BOM для Excel) | `text/csv` |

### 5.4 Асинхронный сбор данных через JS

Клиентский трекер `public/js/tracker.js` отправляет события фоново, не мешая работе страницы.
Путь события показан на схеме: от загрузки страницы до графика на дашборде.

![Путь события от браузера до графика](images/tracking-flow.png)

```js
async function postJson(url, payload, useKeepalive) {
  var response = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload),
    keepalive: Boolean(useKeepalive),
    cache: 'no-store',
    credentials: 'omit'
  });
  if (!response.ok) throw new Error('HTTP ' + response.status);
  return response.json().catch(function () { return {}; });
}

/** Отправляет событие; при неудаче кладёт его в очередь на повтор. */
async function sendEvent(type, extra) {
  if (!consent) return null;
  var payload = basePayload();
  payload.type = type;
  try {
    var result = await postJson(EVENT_URL, payload, false);
    flushQueue();
    return result;
  } catch (err) {
    if (queue.length < MAX_QUEUE) queue.push(payload);
    return null;
  }
}
```

**Что делает трекер**

| Действие браузера | Событие на сервер | Когда |
|---|---|---|
| Открыл страницу | `pageview` (page, origin, referrer, ua, lang, screen, tz) | при загрузке |
| Нажал кнопку формы | `action` + `label` (например `catalog:filter`, `dashboard:apply`) | при клике |
| Страница открыта | `heartbeat` | каждые 30 с |
| Закрыл вкладку или ушёл | `session_end` через `fetch(keepalive)` или `navigator.sendBeacon` | `pagehide`, `visibilitychange` |
| Сеть недоступна | событие попадает в очередь и досылается через `flushQueue()` | при следующем успехе |

### 5.5 Формулы метрик

| Метрика | Формула |
|---|---|
| Просмотры страниц | сумма событий с `type == 'pageview'` |
| Уникальные посетители | число `visitors`, попавших в выбранный период |
| Новые и вернувшиеся | `firstSeen` внутри периода и вне периода |
| Длительность сессии | `(end − start) / 1000`, где `end = lastEvent` при закрытии |
| Средняя длительность сессии | сумма `durationSec` / число сессий |
| Глубина просмотра | сумма `pageViews` / число сессий |
| Показатель отказов | сессии с `pageViews == 1` / все сессии × 100 % |
| Активные сейчас | сессии с событием за последние 5 минут |
| Тип устройства | по User-Agent: `aurora` → `mobile` → `tablet` → `desktop` |
| Источник перехода | пусто → «прямой заход»; хост referrer равен хосту страницы (`origin`) → «внутри сайта»; иначе внешний хост |

## 6. Работа №2. Мобильный клиент под ОС Аврора

### 6.1 WebSocket-канал сервера

Кроме HTTP-API сервер работы №1 предоставляет канал `ws://<адрес>:3000/ws`. Он реализован
вручную по RFC 6455 (`server/websocket.js`: рукопожатие, маскирование кадров, лимит 1 МиБ,
закрытие неверного кадра кодом `1002`) и слой подписок и рассылки (`server/realtime.js`:
рассылка не чаще, чем раз в 0,5 с после изменения данных). Внешних npm-зависимостей в канале
нет.

![Обмен сообщениями приложения с сервером по каналу /ws](images/ws-flow.png)

| От клиента | Поля | Что делает сервер |
|---|---|---|
| `subscribe` | `range` (`24h`, `7d`, `30d`, `all`), `page`, `limit` | запоминает фильтр клиента и присылает снимок статистики |
| `stats`, `refresh` | — | прислать снимок с текущим фильтром |
| `pages` | — | прислать список страниц |
| `track` | `event` (объект как в `POST /api/events`) | записать событие и разослать обновление |
| `ping` | `t` | проверка связи, ответ `pong` |

**Сообщения сервер → клиент**

| От сервера | Поля | Когда приходит |
|---|---|---|
| `hello` | `service`, `version`, `protocol`, `serverTime`, `heartbeatSec` | сразу после подключения |
| `stats` | `data` — тот же объект, что отдаёт `GET /api/stats` | после подключения, `subscribe` и изменений данных |
| `update` | `reason`, `counters`, `serverTime` | при любом изменении данных (лёгкое уведомление) |
| `event` | `reason`, `event`, `counters` | новое событие (для ленты в реальном времени) |
| `pages` | `data` — как `GET /api/pages` | в ответ на `pages` |
| `tracked` | `eventId`, `sessionId`, `counters` | подтверждение записи события из `track` |
| `pong` | `serverTime`, `echo` | ответ на `ping` |
| `error` | `error` | некорректное сообщение или тип |

```

> {"type":"subscribe","range":"all"}
```

### 6.2 Клиент StatClient на C++

`StatClient` — единственный класс сетевой части приложения. Он создаётся в `main.cpp`
и передаётся в QML как контекстное свойство `StatClient`, поэтому QML-страницы читают
статистику как свойства и реагируют на сигналы.

```cpp
connect(m_socket, &QWebSocket::connected, this, &StatClient::onConnected);
connect(m_socket, &QWebSocket::disconnected, this, &StatClient::onDisconnected);
connect(m_socket, &QWebSocket::textMessageReceived, this, &StatClient::onTextMessage);

void StatClient::onConnected()
{
    setConnected(true);
    setStatus(tr("Подключено"));
    m_pingTimer.start();                       // 25 с

    QVariantMap msg;
    msg.insert(QStringLiteral("type"), QStringLiteral("subscribe"));
    msg.insert(QStringLiteral("range"), m_range);
    msg.insert(QStringLiteral("page"), m_pageFilter);
    sendJson(msg);
}

void StatClient::scheduleReconnect()
{
    if (!m_autoReconnect || m_reconnectTimer.isActive())
        return;
    const int delay = qMin(30000, 1000 * (1 << qMin(m_reconnectAttempt, 5)));
    m_reconnectAttempt += 1;
    m_reconnectTimer.start(delay);             // 1, 2, 4, 8, 16, 30 с
}
```

**Свойства и методы StatClient, доступные из QML**

| Свойство или метод | Назначение |
|---|---|
| `connected`, `status`, `lastError` | состояние соединения для индикатора на странице |
| `serverUrl` | адрес канала, читается из `QSettings` (по умолчанию `ws://192.168.1.100:3000/ws`) |
| `stats`, `sessions`, `pages`, `counters` | последний снимок статистики, таблица сессий, список страниц |
| `range`, `pageFilter` | фильтр отчёта: период и страница |
| `autoReconnect`, `live`, `messageCount` | повторные попытки соединения, приём рассылок, счётчик сообщений |
| `connectToServer()`, `disconnectFromServer()`, `reconnect()`, `refresh()` | управление соединением и запрос снимка |
| `requestPages()` | запрос списка страниц |
| `trackPageView(page, label)`, `trackAction(label, page)` | отправка собственных событий серверу |
| `formatDuration(sec)`, `formatTime(ms)` | человекочитаемые длительность («1 ч 02 мин») и время |

Приложение отправляет события с `ua = "AuroraOS aurorastat/1.0"`, поэтому сервер относит их
к устройству `aurora` и они попадают в ту же статистику, что и визиты браузера.
